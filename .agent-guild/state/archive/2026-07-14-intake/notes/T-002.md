# T-002 self-report

Created `.claude/skills/job/SKILL.md` — the `/job` intake skill. Nothing else touched.

## What it does

- Frontmatter: `name: job` + a description written to trigger on "start a job
  from issue 15" / "kick off a job from this spec" / "build issue #12" per the
  spec's example phrasings.
- Body is five numbered steps: classify `$ARGUMENTS` into the six situations
  (bare `#N`, `owner/repo#N`, issue URL, local file, other URL, no argument),
  fetch via the exact `gh issue view ... --json number,title,body,url`
  invocations named in the spec, write the single output file with the
  header-then-content contract, self-check with
  `check-provenance.py <spec.md> [--issue N]`, then hand off to
  `/constitution`.

## Judgment calls

- **`ref` derivation for GitHub issues**: rather than reconstructing
  `owner/repo#N` differently per argument form, I derive it uniformly from the
  `url` field `gh` returns (regex `github\.com/([^/]+/[^/]+)/issues/(\d+)`).
  This guarantees `ref` is consistent regardless of which of the three issue
  forms triggered the fetch — form 1 (bare number) doesn't otherwise carry the
  owner/repo itself. Spec only fixed the format `<owner/repo#N | path | URL>`,
  not the derivation mechanism, so I took the most reliable path.
- **Unrecognized non-empty argument**: the spec names six situations, not a
  seventh "garbage input" case. I added one sentence in step 1 telling the
  agent not to guess and to report what it saw — consistent with the
  never-fabricate rule — without inventing a full seventh code path.
- **Local-file `ref`**: used the path exactly as given in `$ARGUMENTS` (not
  resolved to an absolute path), matching the contract's `<path>` placeholder
  literally.
- Did not run `check-provenance.py --self-test` myself since C-3 (the
  validator's own self-test) is a separate task/clause, not part of C-1/C-2/
  C-7/C-8 assigned here; I did read the validator's source in full to line up
  every key and requiredness rule for C-2.

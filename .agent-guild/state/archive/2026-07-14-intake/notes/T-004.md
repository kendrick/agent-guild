# T-004 self-report

## What I did

- `_lib.py` `project_dir()`: primary `CLAUDE_PROJECT_DIR` path is byte-for-byte
  unchanged. The fallback now computes the two-dirs-up `candidate` and returns
  it only if `candidate/.agent-guild` is a directory; otherwise it raises
  `RuntimeError` naming the candidate path and explaining the plugin scenario
  that motivates the guard. Comment above it extends the existing top-of-file
  "fail loud" rule rather than restating it.
- `test_hooks.py`: added a new `_lib.py project_dir() fallback` section
  (before the `stop-gate.py` section) that imports `_lib` directly in-process
  (subprocess-based `run_hook()` can't exercise this — it always injects a
  valid `CLAUDE_PROJECT_DIR` via env). It pops `CLAUDE_PROJECT_DIR` from the
  parent env, monkeypatches `_lib.__file__` to a fake `.../pkg/hooks/_lib.py`
  path in a scratch dir (no need for the file to actually exist — the
  function only does string/dirname math on it), and exercises both
  branches:
  - scratch dir WITH `.agent-guild/` created → `project_dir()` returns it
    (compared via `os.path.realpath` on both sides, since macOS temp dirs can
    involve a `/var/folders` vs realpath discrepancy).
  - scratch dir WITHOUT `.agent-guild/` → `project_dir()` raises
    `RuntimeError` whose message contains `.agent-guild`.
  Both `__file__` and the popped env var are restored in a `finally` block so
  later subprocess-based tests (which build their own env dict) are
  unaffected.

## Judgment calls

- No seam existed in `project_dir()` for injecting a fake "two dirs up"
  location, and the spec forbids touching any other function or hook runtime
  logic. I test by monkeypatching the `_lib` module's own `__file__` global
  in-process rather than adding a testability parameter to `project_dir()`
  itself — keeps the function's signature and behavior exactly as specified
  while still exercising the real code path for both branches.

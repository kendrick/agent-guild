# T-002 self-report

## What I did

1. Copied all six files from `.agent-guild/hooks/` into `dist/plugin/hooks/`
   verbatim: `_lib.py`, `dispatch-guard.py`, `orchestrator-write-guard.py`,
   `stop-gate.py`, `subagent-return.py`, `test_hooks.py`. Confirmed the five
   non-`_lib.py` files are byte-identical to source via `diff`.

2. Hardened only `dist/plugin/hooks/_lib.py`'s `project_dir()`. The fallback
   ("two directories up from `_lib.py`") is correct in the repo but silently
   wrong inside a plugin, where it would resolve to the plugin's own install
   dir instead of the user's project. Judgment call: rather than leave a
   comment-only flag or hand-correct a path that has no correct answer in a
   plugin context (there's no way to derive the user's project location from
   the plugin's own path), I replaced the silent fallback with a `raise
   RuntimeError(...)`. This follows the module's own stated design rule
   ("Fail loud, fail closed... never a silent exit 0") — a hook that can't
   locate the project is a hook that should block loudly, not misplace state
   beside the plugin. The raise propagates up through `run()`'s existing
   exception handler, which already turns any uncaught exception into a
   `HOOK ERROR` exit-2 block, so no other file needed touching. Left a comment
   above the raise explaining why the in-repo fallback doesn't carry over to
   a packaged build.

3. Verified `python3 dist/plugin/hooks/test_hooks.py` reports "49 passed, 0
   failed" against the packaged copies — the test harness sets
   `CLAUDE_PROJECT_DIR` explicitly for every subprocess call, so the new
   `raise` branch is never exercised by the suite and nothing needed
   updating there.

4. Confirmed via `git diff --quiet HEAD -- .claude .agent-guild/hooks
   .agent-guild/scripts .agent-guild/templates` (no output) that the source
   `.agent-guild/hooks/_lib.py` and everything else in the live kit is
   untouched.

5. Removed a `__pycache__/` directory that appeared under
   `dist/plugin/hooks/` as a byproduct of running the test suite — not one
   of the six named files, so I cleaned it up rather than leave a stray
   build artifact in the deliverable.

## Caveats / judgment calls

- The task file's clause C-6 check_method offers three options (remove,
  correct, or comment-flag the fallback). I chose "remove and replace with a
  loud failure," reasoning it's the only option that both satisfies the
  clause text ("must not depend on that fallback for correctness") and
  matches the file's own pre-existing fail-loud philosophy documented in its
  module docstring. If the checker expected a bare removal with no
  replacement behavior (i.e., let a `None`/`TypeError` surface naturally
  instead of an explicit `raise`), flag it — I judged an explicit, clearly
  worded `RuntimeError` a better fail-loud citizen than an accidental
  `NoneType has no attribute` deep in `os.path.join`.
- Did not touch `dist/plugin/hooks/hooks.json` or the manifest — out of
  scope for this task (that's C-3/C-4, presumably a different task).

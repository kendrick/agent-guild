## Spec excerpt

Write `dist/plugin/README.md` — the install story for the agent-guild plugin,
clear enough that a new user can follow it without reading source. Cover four
things:

1. **Local-path install.** How to install the plugin from a local directory:
   `/plugin marketplace add <path>` then `/plugin install agent-guild` (or the
   `marketplace.json` variant). Note that enablement is recorded in a settings
   file under `enabledPlugins`.

2. **The hybrid, stated plainly.** The plugin ships the agents, skills, and
   hooks — but a plugin CANNOT contribute an always-on CLAUDE.md. So the
   orchestrator contract and the runtime `.agent-guild/state/` must stay in the
   user's own project: they add one line to their root `CLAUDE.md`
   (`@.agent-guild/CLAUDE.md`), create the `.agent-guild/state/` subdirectories,
   and gitignore state. Give the reason, not just the steps.

3. **Explain the import line.** For a reader who later finds `@.agent-guild/CLAUDE.md`
   in their `CLAUDE.md`: say what it is (the orchestrator-contract import), what
   it does (loads the always-on guild rules the plugin can't ship itself), and
   how it got there (you added it when you installed the guild). It must never
   read as a mystery line.

4. **The manual portability check.** How to confirm the four gates fire after
   install: run the offline unit test (`python3 <hooks>/test_hooks.py`) for the
   fast proof, then walk a fresh `claude` session through the gate behaviors — a
   dispatch with no Task-ID is denied, the stop gate holds a turn open while a
   task is unfinished, the write-guard blocks an orchestrator edit of a
   deliverable. Point at the existing `SMOKE.md` Part A as the reference walk.

This is user-facing prose. Before marking the task done, run it through the
`humanizer` skill: invoke the Skill, apply its audit-and-revise loop, and edit
in place. Keep Title Case headings and unspaced chained em dashes; never
hard-wrap prose lines. Write nothing outside `dist/plugin/`.

## Spec excerpt

**This task runs last, after every other task in the job has completed.** That ordering is the whole point of it: several earlier tasks edit files that a build renders into shipped trees, and a regeneration that happens before the last of those edits leaves drift nobody sees.

`.agent-guild/` and `guild-core/` are the authored sources. The same content ships in generated trees:

- `plugin/hooks/`, `plugin/project-template/.agent-guild/`, `plugin/skills/`
- `plugins/agent-guild/` and its own `project-template/`
- `.claude/agents/` and `.claude/skills/`

Earlier tasks changed four build inputs between them: the schema, `ledger-append.py`, its test, and `guild-core/workflows/retrospective/SKILL.md`. Regenerate, then verify:

```sh
python3 scripts/build-plugin.py
python3 scripts/build-plugin.py --check
```

Never hand-edit a file under `plugin/`, `plugins/`, or `.claude/`. They are generated views; the build is the only thing that writes them, and `--check` fails on any drift between a generated tree and a fresh build.

Then confirm the full consumer set is green, all three run every time:

```sh
python3 .agent-guild/scripts/test_ledger_append.py
python3 .agent-guild/hooks/test_hooks.py
python3 scripts/build-plugin.py --check
```

The schema is a shared contract, so every suite that consumes it runs, not just the ledger's own. `test_hooks.py` is in that set because the hooks read state files this contract touches; a past job (#43) scoped a schema change to its own tests and shipped the hook suite red, which the next job's worker inherited as a broken baseline.

If a suite is red, report it — do not fix the underlying code here. That belongs to whichever task owns the file, and a mechanical task quietly patching someone else's artifact is how a job loses track of who verified what.

**Do not commit anything, and do not create a branch.** `git rev-parse HEAD` must still read `164057dbe07d537136677ba3dae139e61ff2c328` when your checker runs. The scope check reads `git status --porcelain` and `git diff --name-only`, both working-tree views: a commit empties them and the check passes having judged nothing.

**The job's only disagreement, and it turns out to be a false one — which is the most instructive result in the set.**

The in-family checker passed all three commands. The courier failed C-5's scope check, on the ground that it had been handed `OK: 17 path(s) in scope` and could not verify a list it was never shown.

Orchestrator ruling: the standard-stem PASS stands. I listed all 17 paths myself and every one is inside the allowlist — the three named files, plus everything under the `.claude/`, `_working-memory/`, `guild-core/workflows/retrospective/`, `plugin/`, and `plugins/` prefixes. The clause is satisfied.

The courier was not wrong about what it could see. It was wrong to convert "I cannot verify this" into "this is false", and that distinction is worth carrying into #34's writeup: a lane that receives evidence rather than access will hit this shape whenever a check reports a conclusion instead of its basis.

Underneath the false disagreement is a true finding, and it belongs to the tooling rather than to this task: **`check-diff-scope.py` prints a count, not the paths it approved.** Nothing downstream of it can audit its judgment — not a courier, not a reader of the verdict, not a person reading the log a week later. The script knows every path it cleared and discards them. That deserves its own issue.

Counts for #34: unique findings, one from the courier, and it is a finding about the evidence rather than about the artifact. Recording it as a plain disagreement would misstate what happened; recording it as a courier error would lose the real defect it exposed.

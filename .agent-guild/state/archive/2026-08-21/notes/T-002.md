# T-002 self-report

## What I did

Added three new regression cases to `scripts/test_build_plugin.py`, appended
inside the existing `with tempfile.TemporaryDirectory(...) as tmp:` block
(they reuse `claude_out`, `claude_installer`, and `install_env` that the
earlier tests in the file already set up):

1. **Upgrade (C-2)** — installs a fresh project, then simulates "clean
   against the record but stale against source" by overwriting one payload
   file's on-disk bytes with synthetic "earlier release" content and
   hand-editing `provenance.json`'s `files` entry to the hash of those same
   bytes (so on-disk == recorded, but both differ from current source).
   Re-installs and asserts the file's bytes now equal current source *and*
   the record's hash for that key equals `sha256(current source)` (not the
   stale hash). Uses `.agent-guild/scripts/ready-set.py` — the exact file
   named in the task's trap warning, as the payload key.

2. **Refusal (C-3)** — installs, then makes a real edit (bytes that don't
   match anything the installer ships) to `.agent-guild/scripts/task-status.py`.
   Re-installs and asserts: the edited bytes survive untouched, exactly one
   `WARNING: ... preserved without writes:` line names that file's
   project-root-relative key, and — the part I judged the actual trap here —
   the record's hash for that key still equals the pre-edit hash (i.e. it was
   never refreshed to match the on-disk edited bytes).

3. **Mixed run (C-3)** — one project with all three payload states at once:
   `check-provenance.py` made clean-but-stale (same technique as case 1),
   `render-verdict.py` given a real edit, and `compose-brief.py` deleted
   outright. One re-install; asserts the stale file upgrades and its hash
   restamps, the edited file is preserved with its original recorded hash,
   the missing file lands matching source, the warning names *only* the
   edited file's key, and `provenance.json`'s `version` field equals the
   running plugin's manifest version.

All three assert on installed bytes and/or `provenance.json`'s contents,
never on a log line alone, per C-9 and the task's instructions.

## How I checked the "would fail pre-job" property

Rather than just reasoning about it, I built the pre-job installer for real:
`git worktree add --detach <scratch> HEAD` (HEAD = 8452b10, the tip before
this job's uncommitted T-001/T-004 changes), ran
`scripts/build-plugin.py --target claude` there to get a pre-job
`install.py`, then ran a scratch-only script (never touching the repo tree)
that reproduces the exact same three scenarios and assertions against that
old installer. All three assertions came back red:

- Upgrade case: no `provenance.json` ever gets written, and the stale bytes
  are left in place (pre-job `_copy_missing` never overwrites an existing
  file).
- Refusal case: bytes and the warning line happen to match (pre-job also
  leaves an edited file untouched and warns), but the hash-in-record
  assertion is unsatisfiable since there's no record at all.
- Mixed case: the stale file is left un-upgraded, *and* the pre-job warning
  names both the stale file and the edited file (since pre-job has no record
  to distinguish "unmodified but old" from "genuinely edited" — it can only
  compare on-disk bytes to current source), so `named_paths == [edited_key]`
  fails on two independent grounds.

I removed the scratch worktree afterward (`git worktree remove --force`);
nothing from that check is in the repo tree.

## Judgment calls / things I'm unsure about

- I picked five existing payload files as fixtures (`ready-set.py`,
  `task-status.py`, `check-provenance.py`, `render-verdict.py`,
  `compose-brief.py`) rather than inventing new ones, on the theory that
  reusing real shipped files is more representative than fabricated
  fixtures. None of them get imported or executed by `install.py` itself —
  they're only ever `shutil.copy2`'d — so overwriting their bytes on disk in
  a scratch project doesn't risk breaking the installer that copies them.
- For the mixed-run case I added a `version` field assertion beyond what the
  spec's three bullets literally ask for, since C-3's text explicitly calls
  out "the run advances the record's version ... even though it preserved a
  file" and it was cheap to check given I already had the record open. It
  doesn't hurt if the checker considers it extra rather than required.
- I did not touch the pre-existing `stale_payload_project` test block
  earlier in the file (drifted file + missing file, no provenance
  assertions). It already exercises adjacent ground but doesn't check the
  record at all, so I left it alone and added new, independent cases rather
  than editing it — in line with "don't touch anything you don't have to."
- I only added `import hashlib` to the top-level imports; no other file was
  touched.

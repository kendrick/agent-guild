## Spec excerpt

Update `docs/installing.md` so it tells the truth about what a re-run of init now does. Four behaviors have to be stated, each accurate against what T-001 shipped:

1. The provenance record is committed with the payload it describes.
2. Re-running init upgrades files that are clean against their recorded hashes.
3. Files differing from their recorded hashes are preserved and named.
4. A pre-provenance project is adopted: what matches is recorded, what differs is preserved and reported.

**The existing table is now wrong, and fixing it is the heart of this task.** It currently says the payload class is one where init "lands each missing file and preserves each differing one." Item 2 makes that false: a file clean against its recorded hash upgrades. The paragraph below the table also ends by calling that missing record "#183", which is this job — it describes as open a gap that is now closed.

**One sentence in that paragraph is load-bearing elsewhere and must survive.** It says `install()` splits the Codex project hooks out of the payload before the drift check runs, so they upgrade on every re-init. The constitution's C-1, its preamble, and `probe-183.py` all cite this document for that definition rather than restating it, so deleting or blurring it breaks their reference. Keep the distinction it draws, because readers get it wrong: the split does not follow the directory layout — those hooks sit inside `.agent-guild/` and look like payload, but provenance governs only what `_copy_missing` can preserve.

Prose standard: this is user-facing documentation, so run it through the `technical-writing` skill and follow its dispatch and audit steps. Do not hard-wrap lines. Chain em dashes flush against the text on both sides.
